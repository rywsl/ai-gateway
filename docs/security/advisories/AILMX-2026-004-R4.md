## Summary

When `trust_xff = true`, a deployment can trust `X-Forwarded-For` as the client identity source. Default configuration is not affected.

## Affected Versions / Configurations

Only deployments that explicitly enable `trust_xff = true` without a trusted proxy boundary are affected. Default `trust_xff = false` deployments are not affected. See `../internal-audit/R4-affected.csv`.

## Impact

If the gateway is directly exposed to the public internet while trusting XFF, callers can choose the apparent client IP used by rate-limit and IP policy logic. This can weaken rate limits and audit attribution.

## Workaround

Keep `trust_xff = false`, or ensure the gateway only receives traffic from a load balancer that strips untrusted client XFF and is listed in `runtime.trusted_proxies`.

## Fix

The WS-5 fix adds CIDR-gated trusted proxy handling and production validation for empty or wildcard trusted proxy lists. Local fix evidence is `ailinkmax-gateway` commit `4afff41fefbf7876d69af2dedb2406fbfad2912a`. Publication remains blocked until production config snapshots confirm whether any public-internet deployment sets `trust_xff = true`.

## Upgrade Guide

Upgrade to the fixed gateway build, keep `trust_xff = false` unless a trusted proxy boundary exists, and validate `runtime.trusted_proxies`.
