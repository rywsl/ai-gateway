## Summary

The legacy JWT verification path checked token expiry without enforcing issuer, audience, or not-before claims. Tenants that lacked the strict auth configuration could accept a token signed for a different tenant.

## Affected Versions / Configurations

Tenants using JWT authentication without a loaded `AuthConfig.global` strict validator are affected. See `../internal-audit/R1-affected.csv`.

## Impact

An authenticated caller with a valid JWT from one tenant could be accepted by another tenant if the target tenant fell back to the legacy verifier. The impact is cross-tenant confidentiality and integrity loss for authenticated API operations.

## Workaround

Deploy strict auth configuration for every tenant and keep `jwt_strict` enabled. Where this is not yet possible, monitor `gw_auth_legacy_jwt_warn_total` and restrict tenant JWT issuers at the edge.

## Fix

The WS-5 fix routes configured auth through `JwtValidator` and WS-15 exposes `jwt_strict` for staged rollout. Final release version, git sha, and enforce date must be filled before publication.

## Upgrade Guide

Upgrade to the fixed gateway build, verify `[flags].jwt_strict = true`, and run the warn-only protocol until legacy-path warnings are below threshold.
