# Egress-impersonate — known gaps

Operational follow-ups carried out of the egress-impersonate landing (Phases 1–5 of
[`docs/spec/07-vendor-integration.md`](../spec/07-vendor-integration.md)).
This file is the operational counterpart of the egress-impersonation section of
[`docs/spec/07-vendor-integration.md`](../spec/07-vendor-integration.md);
update it when an item is resolved or a new gap surfaces in production.

| # | Area | Symptom / question | Mitigation in v1 | Resolution path |
|---|------|--------------------|-------------------|-----------------|
| 1 | OpenAI Codex profile headers | The spec uses `OpenAI-Beta: responses=v1` as the static `OpenAI-Beta` value. The real codex-rs source may diverge by the time this lands. | Header set is fail-static, documented capture procedure; `gw_core::impersonate::openai_codex::headers()` uses the spec values and deviations are not auto-detected. | Before enabling the Codex profile for a production tenant, run `scripts/capture_real_client_headers/codex/capture.sh` against a live session and reconcile. Header-drift CI (Task 6.4) makes this routine. |
| 2 | Codex `x-codex-turn-state` TTL | The `TurnStateCache` TTL is set to 300 s based on an educated guess. Real Codex CLI behaviour may rotate the turn state more aggressively or hold it longer. | TTL is configurable via `[egress].turn_state_ttl_secs`; default 300 s; fail-static, documented capture procedure. | Run Stage 1 with packet capture against a real Codex CLI session and tune the default. |
| 3 | Chrome-class profile choice (D14 #18) | The three `ImpersonateProfile`s now use distinct Chrome-class TLS/HTTP-2 fingerprints (`ClaudeCodeChrome131` -> `Chrome131`, `OpenAiCodex` -> `Chrome133`, `GeminiCli` -> `Chrome132` in `crates/gw-egress-impersonate/src/profiles.rs`), so their JA3/JA4 are no longer identical. The per-identity *static-header* layer is also differentiated per profile (`gw_core::impersonate::{claude_code,openai_codex,gemini_cli}`). | Short-term fix: avoid the batch-identifiable "everything is Chrome131" fingerprint while staying in a high-pass-rate Chrome-class family. `wreq-util 3.0.0-rc.11` was checked locally and exposes browser families (Chrome/Edge/Opera/Firefox/Safari/OkHttp) but no Node/undici profile, so Gemini CLI remains deliberately over-impersonated until a first-class Node/undici emulation exists and passes verification. | No Rust code action pending. If a profile's upstream starts blocking Chrome-class fingerprints, add a dedicated `wreq_util::Emulation` variant in that arm and update this row. Metric to watch: 401/403 ratio per profile after Stage 1. |
| 4 | `wreq` version policy | `wreq` and `wreq-util` follow upstream Chrome version drift; pinning vs floating both have costs. Floating risks silent fingerprint changes; pinning rots the impersonation. | v1 pins `wreq = 6.0.0-rc.28`, `wreq-util = 3.0.0-rc.11`. Header-drift CI checks application headers only. | Re-evaluate quarterly. Header-drift CI cannot catch `wreq` TLS / HTTP-2 fingerprint drift; the early warning for pinned `wreq = 6.0.0-rc.28` / `wreq-util = 3.0.0-rc.11` is `crates/gw-egress-impersonate/tests/self_fingerprint.rs`; a `wreq` bump that changes cipher suites, supported groups, or the GREASE-filtered extension set fails that test. Chrome/BoringSSL extension order is intentionally permuted, so order-only drift is not pinned. |
| 5 | CLI client version pool refresh | Static client-version constants (Claude Code, Codex, Gemini CLI) embedded in the profile pools go stale as those CLIs ship new releases. | Initial pools were captured at landing time; manual refresh only. `.github/workflows/header-drift.yml` (Task 6.4) reminds maintainers when the public CLI version moves. | Phase 7: evaluate an auto-PR bot that diffs the upstream CLI releases against `crates/gw-core/src/impersonate/profile/*.rs` and opens PRs. |
| 6 | Performance SLO | The `loopback_rtt_seconds` p99 SLO is 200 µs (UDS). If we exceed it, where does the regression go first? | Metric is exported and `deploy/prometheus/egress-rules.yml` wires `EgressImpersonateUpstreamTtfbP99High`. Production gateway RTT includes real upstream latency, so the pure-overhead 200 µs SLO remains gated by the Phase-6 microbench (Task 6.2); the alert is a coarser production guard at 30 s, not the microbench SLO. | A sustained breach triggers an issue. Options in order of preference: `ClientPool` cache tuning, `hyper` keep-alive tuning, profile bind sharding, reverting that specific vendor to direct egress. Reverting to "Approach A" (rustls + custom fingerprint) is the last resort. |
| 7 | `identity_snapshot` admin overrides | If an operator hand-edits the `identity_snapshot` JSON column, should the lazy-persist path overwrite it on the next request? | v1 rule: lazy-persist only fires when the column is `IS NULL`; non-null values are trusted as-is. | Go control plane must expose an explicit "regenerate identity" action that sets `vendor_keys.identity_snapshot = NULL` and increments `version` so Rust L1/L2 caches miss and the next request re-derives via `ensure_identity`. Until that ships, ops can run `UPDATE vendor_keys SET identity_snapshot = NULL, version = version + 1 WHERE id = ...`. Contract: [`docs/go-contracts/contract-change/2026-05-29-vendor-validation.md`](../go-contracts/contract-change/2026-05-29-vendor-validation.md). |
| 8 | Tunnel ↔ impersonate mutual exclusion | `pick_peer` enforces "a vendor cannot both tunnel and impersonate" at request time via `GW_TUNNEL_IMPERSONATE_CONFLICT`. The admin-update path does not check this. | Runtime fail-closed remains authoritative — the conflict cannot send a packet to the wrong place. | Go control plane should reject vendor/vendor-key updates that combine `egress_mode = Impersonate` with tunnel-eligible keys (`tunnel_preference.require_tunnel` or Go node mapping). Contract: [`docs/go-contracts/contract-change/2026-05-29-vendor-validation.md`](../go-contracts/contract-change/2026-05-29-vendor-validation.md). |
| 9 | `identity_snapshot` loader read path | `PgSnapshotWriter` writes to the dedicated `vendor_keys.identity_snapshot` column (migration 0009), but the original `VENDOR_KEY_SQL` only selected `payload, version` and `VendorKeyRow` looked for the snapshot inside `payload.identity_snapshot`. The persisted column was therefore never surfaced to `VendorKey.identity_snapshot`, so every cold load re-derived from RNG and any future `wreq` bump would silently shift the fingerprint of "persisted" keys. | Resolved: `VENDOR_KEY_SQL` now folds the column into payload via `jsonb_set(payload, '{identity_snapshot}', COALESCE(identity_snapshot, 'null'::jsonb), true)`, mirroring the `signature_secret` trick in `API_KEY_SQL`. Regression-guarded by the Docker-gated ignored test `e2e_impersonate::identity_snapshot_round_trips_through_postgres`, which seeds a key, persists via the real queue, then re-loads through a fresh `EntityStore` (cold L1/L2) and asserts the upstream User-Agent is identical across both requests. | Local gate: `cargo test -p gw-gateway --test e2e_impersonate -- --ignored identity_snapshot_round_trips_through_postgres`. This checkout has no generic Rust ignored-test GitHub Actions lane to edit; if one is added, it must include `gw-gateway` so this test runs in CI. |
| 10 | macOS bench: TCP loopback ephemeral-port exhaustion | `cargo bench -p gw-egress-impersonate --bench loopback_rtt` panics on Darwin with `Os { code: 49, AddrNotAvailable }` after the UDS group completes. 50 k rapid TCP connect/close cycles exhaust the 16 k ephemeral-port range left by macOS's default `net.inet.ip.portrange.first/last`. UDS (the default `gw-proxy` egress transport) measured 201–203 µs p99, within SLO (Gap #6). | Environmental, not a code defect: the TCP path is exercised by E2E and unit tests, not this Darwin bench; UDS is what production runs. | Run the bench on Linux CI (default ephemeral range ≈ 28 k–60 k), or for local Darwin runs widen the port range via `sudo sysctl -w net.inet.ip.portrange.first=10000`. |
